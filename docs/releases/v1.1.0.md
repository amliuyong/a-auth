# A Auth v1.1.0 release notes

This source revision adds agent-payment authorization, administrator and
account workflows, public SDK onboarding and configurable commercial AWS
Regions to the stable HTTP API.

## Compatibility and distribution

The release uses Semantic Versioning for the HTTP API described by
`openapi/openapi.json` and the public TypeScript/Python resource-server SDK APIs.
Deployment configuration and persisted formats remain outside that guarantee.
Review the upgrade notes below before changing a deployment.

Rust workspace and OpenAPI metadata identify this source as 1.1.0. GitHub
source releases provide archives; Rust crates remain unpublished. The
resource-server SDKs are distributed separately as `agent_auth_rs` 1.0.2 on
[npm](https://www.npmjs.com/package/agent_auth_rs/v/1.0.2) and
[PyPI](https://pypi.org/project/agent-auth-rs/1.0.2/). Their immutable
`rs-sdk-v1.0.2` tag and published artifacts are unchanged by this source release.

## User-facing changes

- **Agent payments:** immutable, single-transaction intent and terms; fresh
  strong user consent for one workload; one-hop delegated execution, bounded
  idempotency and recovery; and payment-verification SDK helpers. The feature
  is disabled unless a payment resource is configured. Acceptance uses a
  controlled synthetic channel; no real payment channel is supported.
- **Authorization visibility:** the account page shows approved actors or
  patterns, delegation limits, resources, scopes and expiry. Grant revocation
  reloads actual server state. Online introspection enforces revocation;
  offline JWT verification can continue accepting a token until expiry.
- **Administrator tools:** security-event filtering, cursor pagination, event
  detail and delivery status; Okta/Entra/generic OIDC templates with staged
  diagnostics; and self-hosted login/consent branding with built-in choices,
  isolated preview, durable revisions and reset. SaaS branding is unsupported.
- **Onboarding:** scenario-based guidance and independent examples for PKCE,
  device authorization, refresh, workload exchange, protected MCP calls and
  revocation, using the public SDKs.
- **MCP interoperability:** recorded loopback TLS checks with mcp-remote 0.15.2,
  MCP Inspector mcpdo 2.11.0 and mcp-auth 0.2.0, including natural-expiry refresh.
  Inspector GUI, production/AWS and actual-client DPoP interoperability remain
  outside those checks.
- **AWS deployment:** configurable commercial primary and standby Regions,
  deployment-cost guidance, and a new product logo and introduction video.

## Upgrade notes

Read the [deployment runbook](../INSTALL_DEPLOY.md),
[Region/failover guide](../MULTI_REGION_FAILOVER.md),
[federation guide](../FEDERATION_TEMPLATES.md),
[branding contract](../BRANDING.md) and [payment contract](../AGENT_PAYMENT.md).

`CDK_DEFAULT_REGION` selects the business primary Region; `SAAS_REPLICA_REGIONS`
and `SAAS_STANDBY_REGION` select one different standby. The supported partition
is commercial `aws`. CloudFront certificates, global WAF/logs and Lambda@Edge
remain in us-east-1. Another primary Region creates a separate edge stack and
needs bootstrap in both Regions. Region enablement, service availability,
quotas, deployment and failover require separate verification. Existing
us-east-1 resource paths are preserved.

SaaS federation secrets must be explicitly provisioned under
`agent-auth/federation/<tenant>/`. Replace legacy references outside that
namespace; templates do not move secrets. Both configuration and login enforce
public endpoint and tenant-bound secret restrictions.

Existing self-hosted installations without a branding record keep the default
appearance. Branding uses the existing administrator-authentication table and
rejects stale revisions and unsupported future stored versions. Payment
configuration is opt-in and does not provide a production payment channel.

## Security and evidence boundaries

MCP SDK 1.32.0, patched Vite/test dependencies, certifi 2026.10.19 and
markdown-it 15.0.3 address the documented dependency findings. Documentation
tooling still contains unpatched braces 3.0.3 under GHSA-vfj7-8cjw-p6xm.
Repository npm audit remains **FAIL_UNPATCHED_UPSTREAM**, tracked in
[Issue #111](https://github.com/amliuyong/a-auth/issues/111): one underlying High
advisory affects five dependency nodes. It is a documentation development
dependency; no downgrade, vendor patch or audit suppression is applied.
Lambda Function URLs remain prohibited.

The public SDK 1.0.2 registry-install and controlled TLS checks, historical SDK
1.0.1 AWS checks, and third-party loopback results retain their distinct source
and environment bindings. They do not prove that this release's AWS deployment
or a real external payment/workload platform has passed acceptance.

Source CI and the external release gate provide separate evidence. The
[external contract](../EXTERNAL_CONFORMANCE.md) requires the fixed OIDF Basic OP
code-flow plan and selected project-owned RFC 9700 regressions against the exact
deployed candidate, with any official non-PASSED outcomes bound to active,
owner-approved exceptions. Prior v1.0.0 deployment evidence does not qualify
this candidate. A merge or a watchdog success is not permission to publish a
protocol claim.

Project test results are not standards-body certification. FAPI, OpenID
Federation and blanket RFC 9700 certification remain explicit non-claims.
Candidate SHA, source checks, deployment identity and candidate-specific
release-gate evidence accompany the release draft.
