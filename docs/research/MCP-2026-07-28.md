# MCP 2026-07-28 正式版研究

> 研究日期：2026-07-29
> 比较基线：MCP `2025-11-25` 正式版
> 来源范围：仅使用 Model Context Protocol 官方网站，以及
> `github.com/modelcontextprotocol` 组织下的规范、扩展和 SDK 仓库。

## 1. 结论摘要

1. **`2026-07-28` 已正式发布。** 官方 GitHub Release 明确标记为
   “stable release”，发布时间为 `2026-07-28T16:47:49Z`，tag 和规范版本标识均为
   `2026-07-28`；tag 指向 commit
   [`5f5440bb26a62e2cf3440b92da5a667efa03b267`](https://github.com/modelcontextprotocol/modelcontextprotocol/commit/5f5440bb26a62e2cf3440b92da5a667efa03b267)。
   [正式 Release](https://github.com/modelcontextprotocol/modelcontextprotocol/releases/tag/2026-07-28)；
   [正式规范](https://modelcontextprotocol.io/specification/2026-07-28)；
   [官方 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)。
2. **这是一次有意的 breaking protocol revision。** 核心从
   “初始化握手 + 连接/会话状态 + server-initiated request”转为
   “每请求自描述 + 无协议会话 + MRTR”。只支持 `2026-07-28` 的 modern 实现不能与
   只支持 `2025-11-25` 的 legacy 实现直接互通；兼容依赖 dual-era
   client/server，而不是新协议自身自动兼容。
   [版本与兼容性](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)。
3. **授权方面主要是安全加固，而不是替换 OAuth 基线。** PRM、OAuth/OIDC
   discovery、resource indicators 和 CIMD 在上一版已经存在；本版最重要的增量是：
   RFC 9207 `iss` 校验、DCR `application_type`、凭据按 AS `issuer`
   隔离、step-up scope 累积、refresh-token 指引，以及将 DCR 正式标为
   Deprecated、优先迁移到 CIMD。
   [授权规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)；
   [客户端注册](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)。
4. **Enterprise-Managed Authorization（EMA）不是核心 `2026-07-28`
   规范的一部分。** 它是 `ext-auth` 仓库中独立版本化的 **Stable**
   授权扩展；OAuth Client Credentials 则是同一仓库中的独立 **Draft**
   扩展。二者均为 opt-in，不能因为核心版本升级而推定已启用或必须实现。
   [EMA Stable 规范](https://github.com/modelcontextprotocol/ext-auth/blob/fb374c7db2b34f18ca9183882e0beecdf661892b/specification/stable/enterprise-managed-authorization.mdx)；
   [Client Credentials Draft](https://github.com/modelcontextprotocol/ext-auth/blob/fb374c7db2b34f18ca9183882e0beecdf661892b/specification/draft/oauth-client-credentials.mdx)。
5. **对 `agent-auth` 没有立即的 core transport 改造。** 本仓库是 Authorization
   Server 与 RS auth SDK，不实现 MCP JSON-RPC transport，因此无状态化、
   `server/discover`、MRTR、subscriptions 等 major changes 应由实际 MCP
   client/server 仓库处理。这里的直接工作面是 CIMD、scope challenge、path-based
   PRM 和可选 EMA。

本文使用下列强度标记：

- **MUST / REQUIRED**：互操作所需的强制要求。
- **SHOULD / RECOMMENDED**：通常应实现，偏离时应有明确理由。
- **MAY / OPTIONAL**：可选能力；若选择实现，仍须满足该能力内部的 MUST。
- **Breaking**：切换到 `2026-07-28` wire behavior 后，旧 peer 不能无适配继续工作。
- **Non-breaking**：新增可选能力、放宽约束、指导性要求，或在 dual-era
  分流下不改变 legacy wire behavior。
- **Deprecated**：本版仍可工作，但新实现 SHOULD NOT 采用，并进入移除周期。

| M8 | 所有 modern result **MUST** 带 `resultType`；普通结果为 `complete`，MRTR 中间结果为 `input_required`。client 收到 earlier-protocol server 缺失该字段时 **MUST** 视为 `complete`；未知值 **MUST** 视为无效。 | modern wire 的结果 shape 有 breaking 变化；强制 fallback 使 modern client 可读 legacy result。dual-era server 不应把 modern 字段泄漏到 legacy wire。 | [Responses / ResultType](https://modelcontextprotocol.io/specification/2026-07-28/basic#resulttype)；[SEP-2322 PR](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2322) |

MRTR 的额外安全义务值得单列：`requestState` 是 attacker-controlled input；如果它影响授权、
资源访问或业务逻辑，server **MUST** 做完整性保护并拒绝校验失败的状态。若业务要求严格
single-use，server **MUST** 在服务端保存并执行一次性约束；仅把状态做成签名 blob 不足以防止
窗口内 replay。[MRTR server requirements](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr#server-requirements-basic-workflow)。

## 4. Authorization 深入分析

### 4.1 先划清三条规范线

| 规范线 | 状态 | 是否随 core `2026-07-28` 强制启用 | 发现/协商方式 |
| --- | --- | --- | --- |
| Core Authorization | `2026-07-28` core 的一部分；Authorization 整体对 MCP implementation 是 **OPTIONAL**，但选择 HTTP Authorization 后内部 MUST 生效 | 否；未启用 Authorization 的实现不因此必须增加 OAuth | PRM → AS metadata；核心要求见[授权规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) |
| Enterprise-Managed Authorization | `ext-auth` 中独立 **Stable** 扩展；2026-06-17 由 draft 提升 stable | 否；optional/additive/independently versioned | Stable 规范要求在 AS metadata 的 `authorization_grant_profiles_supported` 中发现 ID-JAG profile。[固定规范](https://github.com/modelcontextprotocol/ext-auth/blob/fb374c7db2b34f18ca9183882e0beecdf661892b/specification/stable/enterprise-managed-authorization.mdx#6-discovery)；[stable promotion commit](https://github.com/modelcontextprotocol/ext-auth/commit/877b4fdfac6da002305a33086fccd887ce69ee98) |
| OAuth Client Credentials | `ext-auth` 中独立 **Draft** 扩展，`Protocol Revision: draft` | 否；不得当作 core 或 stable 要求 | 采用后必须满足 core Authorization；使用预注册凭据，不使用 DCR。[固定 Draft](https://github.com/modelcontextprotocol/ext-auth/blob/fb374c7db2b34f18ca9183882e0beecdf661892b/specification/draft/oauth-client-credentials.mdx) |

官方 EMA overview 展示了 per-request extension capability 声明，但当前 Stable normative
文档第 6 节定义的互操作发现信号是 AS metadata 中的
`authorization_grant_profiles_supported`。实现时应以 Stable normative 文档为准，并可将
capability 声明作为额外产品协商信号，不能用它替代 AS metadata discovery。
[EMA overview](https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization)；
[EMA Stable §6](https://github.com/modelcontextprotocol/ext-auth/blob/fb374c7db2b34f18ca9183882e0beecdf661892b/specification/stable/enterprise-managed-authorization.mdx#6-discovery)。

### 4.2 PRM 与 OAuth/OIDC discovery

以下是 **沿用的 core 基线**，不是本版新引入：

- MCP server 作为 RS，若支持 Authorization，**MUST** 实现 RFC 9728 Protected
  Resource Metadata；PRM **MUST** 含至少一个 `authorization_servers`。
- server **MUST** 至少提供 `WWW-Authenticate: ... resource_metadata=...` 或
  well-known PRM 机制之一；client **MUST** 同时支持两种，并优先使用 challenge
  中的 URL，否则按 MCP endpoint path、origin root 顺序回退。
- AS **MUST** 至少暴露 RFC 8414 或 OIDC Discovery 之一；MCP client **MUST**
  支持两者。issuer 有 path 时，client 按 OAuth path insertion、OIDC path
  insertion、OIDC path append 的顺序探测；无 path 时探测 OAuth、再 OIDC。

完整规则见
[Authorization Server Discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery)。

本版增量加固有两点：

1. 明确 MCP 使用 RFC 8414 默认 `oauth-authorization-server` suffix，不定义 MCP
   私有 suffix。这是澄清，不改变上一版既有 endpoint 顺序。
   [SEP-2351 PR](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2351)。
2. client 取得 metadata 后 **MUST** 验证其中 `issuer` 与构造 well-known URL
   时使用的 issuer identifier 完全相同；不相同 **MUST NOT** 使用该 metadata。
   [metadata validation](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery#authorization-server-metadata-discovery)。

PRM 可列多个 AS，但它们是彼此独立的 OAuth AS。选择由 client 完成；每个 AS 的
credentials/tokens 必须分区，不能把“同一 MCP resource”误当成“同一 client
registration namespace”。
[Authorization Server Location](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery#authorization-server-location)。

### 4.3 DCR deprecated → CIMD

核心仍支持三种 client ID 获得方式，支持全部方式的 client **SHOULD** 按以下优先级：

1. 已有 pre-registration；
2. AS metadata 声明 `client_id_metadata_document_supported=true` 时使用 CIMD；
3. AS metadata 有 `registration_endpoint` 时才以 DCR fallback；
4. 都不可用时提示用户输入预注册信息。

[Client Registration priority](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)。

**CIMD 仍是双方 SHOULD，而不是无条件 MUST。** 一旦选择实现 CIMD：

- client ID **MUST** 是带 path 的 HTTPS URL；
- 文档至少 **MUST** 有 `client_id`、`client_name`、`redirect_uris`；
- 文档内 `client_id` **MUST** 与 URL 完全相同；
- AS **SHOULD** fetch/cache 文档，且 **MUST** 校验 JSON、必填字段、精确
  client ID 和请求的 redirect URI；
- AS 需要处理 SSRF、localhost impersonation，并 **MAY** 建立 domain trust policy。

[CIMD requirements](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration#implementation-requirements)；
[CIMD security](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations#client-id-metadata-document-security)。

**DCR 在本版只是 Deprecated，并未删除。** 双方仍 **MAY** 实现，目的是兼容不支持
CIMD 的 AS。新增的 DCR 强制项是 client **MUST** 发送正确
`application_type`；这不适用于 CIMD 或 pre-registration。
[DCR](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration#dynamic-client-registration)；
[PR #2858](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2858)；
[SEP-837](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/837)。

### 4.4 RFC 9207 `iss` 与 issuer-bound credentials

#### Authorization response `iss`

client 在跳转浏览器前 **MUST** 从已经验证的 AS metadata 记录 expected issuer，并与
PKCE verifier/`state` 置于同一请求记录。AS **SHOULD** 在成功和错误 authorization
response 中都返回 `iss`；返回时 **MUST** 在 metadata 中声明
`authorization_response_iss_parameter_supported=true`。

client 在把 code 发到任何 token endpoint 前 **MUST** 按下表处理：

| metadata flag | response 中 `iss` | client 动作 |
| --- | --- | --- |
| `true` | 有 | 与 recorded issuer 做 simple string comparison |
| `true` | 无 | **拒绝** |
| `false`/缺失 | 有 | 仍须比较 |
| `false`/缺失 | 无 | 当前可继续 |

比较前 **MUST NOT** 做 scheme/host 大小写折叠、默认端口消除、尾斜杠或百分号编码
normalization。错误响应也同样校验；issuer mismatch 时 client **MUST NOT** 处理或显示
其中的 `error`、`error_description`、`error_uri`。
[Authorization Response Validation](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#authorization-response-validation)；
[SEP-2468](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2468)。

#### 凭据与 token 的 AS 绑定

- pre-registered credentials 和 DCR credentials **MUST** 以 AS metadata 的
  `issuer` 为 key 持久化；
- AS 改变时 **MUST NOT** 复用旧 AS 凭据，且 **MUST** 重新注册；
- 对 pre-registration，issuer 不符时 client **SHOULD** 明确报错，而不是静默尝试；
- CIMD client ID 是 AS 按需解析的自托管 HTTPS URL，可跨 AS 使用，不需要重新注册；
  但各 AS 签发的 token 仍必须隔离。

[Authorization Server Binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration#authorization-server-binding)；
[SEP-2352](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2352)。

### 4.5 Resource indicators 与 RS token validation

这是沿用的 core 安全基线：

- client **MUST** 在 authorization request 和 token request 中都发送 `resource`，
  且无论 AS 是否声称支持都必须发送；
- `resource` **MUST** 标识目标 MCP server；client **SHOULD** 使用能提供的最具体
  canonical URI；
- MCP server/RS **MUST** 验证 token 是专门签发给自己的，只接受适用于自身 resource
  的 token；
- MCP server **MUST NOT** 接受或转发其他 token；调用上游 API 时必须使用上游 AS
  另行签发的 token。

[Resource Parameter Implementation](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#resource-parameter-implementation)；
[Token Audience Binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations#token-audience-binding-and-validation)；
[Access Token Privilege Restriction](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations#access-token-privilege-restriction)。

### 4.6 Scope challenge 与 step-up

初次未授权时，RS **SHOULD** 在 `WWW-Authenticate` 中给出当前访问所需 `scope`；
没有 challenge scope 时，client **SHOULD** 使用 PRM 的 `scopes_supported`，再没有就
省略 `scope`。challenge scope 对**当前 operation**具有权威性，client **MUST NOT**
假设它与 `scopes_supported` 存在子集关系。

运行中 token 权限不足时，RS **SHOULD** 返回 HTTP 403，并在 Bearer challenge 中给出
`error="insufficient_scope"`、当前 operation 所需的完整 scope 集、`resource_metadata`
以及可选 `error_description`。RS 不负责回显 client 以前拥有的 scopes；scope
accumulation 是 client 责任。

client 进行 step-up 时 **SHOULD** 请求：

```text
previously requested scopes ∪ current challenge scopes
```

并限制重试次数、记录同一 resource/operation 的升级尝试。RS 判断 token 是否足够时
**MUST** 考虑“宽 scope 蕴含窄 scope”的 hierarchy，不能只做字符串集合包含。

[Scope Selection](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#scope-selection-strategy)；
[Scope Challenge Handling](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#scope-challenge-handling)；
[SEP-2350](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2350)。

refresh token 指引也是本版新增：client **MUST** 安全保存 refresh token，**SHOULD**
在 client metadata 中包含 `refresh_token` grant；仅当 AS 的 `scopes_supported`
包含 `offline_access` 时 **MAY** 请求，且 **MUST NOT** 假设 AS 一定签发。RS
**SHOULD NOT** 在 PRM 或 challenge 中加入 `offline_access`，因为它不是 resource
访问要求。
[Refresh Tokens](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#refresh-tokens)；
[SEP-2207](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2207)。

## 5. Enterprise-Managed Authorization（独立 Stable 扩展）

EMA 的目标是把企业 IdP 纳入 MCP access-token 签发链，由企业策略决定
user/client/server/scope 组合是否允许，而不是让每位用户逐个对 MCP server 授权。
它不修改 core Authorization 的 PRM、AS discovery、resource audience 和 RS validation
义务。

规范流程是：

1. 用户通过 OIDC 或 SAML 登录 MCP client，client 得到 identity assertion；
2. client 在企业 IdP 做 token exchange，得到 ID-JAG；
3. client 把 ID-JAG 作为 JWT bearer authorization grant 提交给 MCP resource AS；
4. resource AS 校验 ID-JAG 并签发 audience-restricted MCP access token；
5. client 用该 token 调 MCP RS。

关键 normative 要求：

- 请求 ID-JAG 时 `audience` **MUST** 是 resource AS 的 issuer；
- `resource` 是 **OPTIONAL**，但出现时 **MUST** 是 MCP server 的 resource identifier；
- ID-JAG 中 `resource` claim 若出现，**MUST** 是 MCP server identifier；
- resource AS 最终签发的 access token **MUST** audience-restricted 到 ID-JAG
  `resource` 标识的 MCP server；
- client 可用 pre-registration；未预注册时可用 CIMD client ID，并可选
  `private_key_jwt`；
- AS 通过 metadata
  `authorization_grant_profiles_supported` 包含
  `urn:ietf:params:oauth:grant-profile:id-jag` 宣告支持；
- 企业 IdP 能看到并控制 token issuance，但规范明确其可见性不延伸到 client 与
  MCP server 之间的实际 MCP traffic。

[EMA Stable fixed source](https://github.com/modelcontextprotocol/ext-auth/blob/fb374c7db2b34f18ca9183882e0beecdf661892b/specification/stable/enterprise-managed-authorization.mdx)；
[官方 EMA 博客](https://blog.modelcontextprotocol.io/posts/enterprise-managed-auth/)；
[SEP-990 PR](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/990)。

`ext-auth` 当前没有用 core date tag 表示 EMA 版本；Stable 是仓库目录/状态，独立于
core release。消费方应固定 ext-auth commit 或自己记录所实现的扩展版本，而不是写成
“MCP 2026-07-28 自带 EMA”。
[ext-auth repository](https://github.com/modelcontextprotocol/ext-auth)；
[stable promotion commit](https://github.com/modelcontextprotocol/ext-auth/commit/877b4fdfac6da002305a33086fccd887ce69ee98)。

## 6. OAuth Client Credentials（独立 Draft 扩展）

该扩展用于无人值守 machine-to-machine client，目前仍是 **Draft**，不能作为
`2026-07-28` core conformance 要求，也不能与 Stable EMA 等同。采用该扩展时：

- extension 自身 optional，但采用者 **MUST** 同时符合 core Authorization；
- 仅用于 HTTP transport；
- 使用 out-of-band pre-registered client credentials，明确**不使用 DCR**；
- client **MUST** 使用 JWT authentication 或 client secret；JWT 为
  **RECOMMENDED**；
- AS metadata **MUST** 在 `token_endpoint_auth_methods_supported` 至少包含
  `private_key_jwt` 或 `client_secret_basic`；支持 JWT 时还需要
  `token_endpoint_auth_signing_alg_values_supported`；
- token request 仍带 core 要求的目标 `resource`，RS 仍执行 audience/scope 校验。

[Client Credentials Draft fixed source](https://github.com/modelcontextprotocol/ext-auth/blob/fb374c7db2b34f18ca9183882e0beecdf661892b/specification/draft/oauth-client-credentials.mdx)；
[官方扩展说明](https://modelcontextprotocol.io/extensions/auth/oauth-client-credentials)。

## 7. 兼容性矩阵

### 7.1 Modern / legacy / dual-era wire compatibility

`modern` 指 `2026-07-28+` 每请求 metadata 模型；`legacy` 指
`2025-11-25-` initialize 模型；`dual-era` 同时实现两者。

| Client \ Server | Modern-only | Dual-era | Legacy-only |
| --- | --- | --- | --- |
| Modern-only | **可用**；版本不匹配时处理 `-32022` | **可用**；走 modern | **失败**；没有 legacy fallback |
| Dual-era | **可用**；保持 modern | **可用**；通常探测后走 modern，也能按连接入口服务 legacy | **可用**；探测后回退 `initialize` |
| Legacy-only | **失败**；不会 fall-forward | **可用**；server 走 legacy 行为 | **可用**；按 legacy revision |

HTTP dual-era client 只有在 `400/404/405` 且 body 不是 recognized modern JSON-RPC
error 时才回退；recognized modern error 表示对端是 modern，应按 supported version
重试而不是误判 legacy。stdio dual-era client **SHOULD** 先发 `server/discover`。
[官方完整矩阵](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning#compatibility-matrix)；
[HTTP backward compatibility](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#backward-compatibility)。

### 7.2 按角色的迁移与兼容策略

| 角色 | `2026-07-28` 必做（MUST/REQUIRED） | 建议（SHOULD） | 兼容策略与主要风险 |
| --- | --- | --- | --- |
| MCP server | 实现 `server/discover`；按每请求 `_meta` 校验 version/capabilities；不依赖 session；所有结果带 `resultType`；cacheable complete result 带 `ttlMs/cacheScope`；HTTP 校验标准 headers；用 MRTR 和 `subscriptions/listen`。 | 每结果带 `serverInfo`；list 稳定排序；需要覆盖旧 client 时实现 dual-era。 | modern-only 会拒绝 legacy client。dual-era 必须按 era 使用不同 wire schema，尤其不能向 legacy result 泄漏 `resultType`/cache fields。 |
| MCP client | 每请求带 protocolVersion/capabilities；HTTP 带版本、method、条件性 name headers；处理 `-32022`；支持 `x-mcp-header`；识别 MRTR/subscription；旧 server 缺 `resultType` 时当 complete；流断线用新 ID 重发。 | 调 `server/discover`、缓存 era verdict；遵守 TTL；接受旧 `-32002`；实现 retry limit 与业务幂等。 | 需要连接旧 server 时做 dual-era probe/fallback。不能把 auth 401/403 或 recognized modern error 当作 legacy 证据。 |
| Authorization Server | 若服务 MCP Authorization，至少提供 RFC 8414/OIDC discovery 之一；遵守 OAuth 2.1/PKCE；返回 `iss` 时 metadata flag **MUST** 为 true。 | authorization response（含 error）带 `iss`；支持 CIMD 并声明 capability；DCR/OIDC 部署理解并校验 client 发送的 `application_type`；正确发布 refresh-token metadata。 | `application_type` 的 MCP **MUST** 直接约束 client，AS 是否按 OIDC 规则拒绝由其策略决定。`iss`/metadata 必须与公开 issuer 完全一致。DCR 尚可兼容但已 Deprecated；新接入优先 pre-registration/CIMD。EMA 和 client-credentials 只有显式采用对应独立扩展才增加义务。 |
| RS SDK / auth middleware | 生成/服务 PRM，`authorization_servers` 非空；支持 challenge `resource_metadata`；验证 token 的 issuer、有效性、目标 audience/resource；禁止 token passthrough；401/403 语义正确；按 operation 校验 scopes。 | 401/403 challenge 给出当前操作所需完整 scope；提供 endpoint-path 与 root PRM fallback；scope hierarchy-aware；对公开 cacheScope 做授权边界保护。 | RS SDK 不应接管 AS client registration，但必须把 canonical resource identifier、PRM、challenge 和 token validator 配成同一值。支持旧 client 不得放松 audience validation。 |

角色要求依据：
[Versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)；
[Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)；
[Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)；
[Authorization Security](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)。

## 9. 对 `agent-auth` 当前实现的影响

本节是对当前仓库实现的本地代码审计，不是官方 MCP 规范原文。core transport 与 authorization 的职责必须
分开判断：本仓库没有 MCP JSON-RPC transport，因此不能、也不应在这里实现
`server/discover`、MRTR、`subscriptions/listen` 或 modern/legacy wire codec。

### 9.1 已对齐的授权基线

| 能力 | 当前证据 | 结论 |
| --- | --- | --- |
| PRM | [`crates/discovery/src/prm.rs`](../../crates/discovery/src/prm.rs) 生成 `resource`、`authorization_servers`、`bearer_methods_supported` 和可选 `scopes_supported`；[`crates/http/src/prm.rs`](../../crates/http/src/prm.rs) 提供控制面生成和 BYOD root well-known 投放 | core PRM 基线已具备 |
| OAuth/OIDC discovery | [`crates/discovery/src/metadata.rs`](../../crates/discovery/src/metadata.rs) 同时生成 RFC 8414 与 OIDC metadata，并宣告 `registration_endpoint`、PKCE S256 和实际 grant/auth methods | discovery 基线已具备 |
| RFC 9207 `iss` | metadata 宣告 `authorization_response_iss_parameter_supported=true`；[`crates/http/src/authorize.rs`](../../crates/http/src/authorize.rs) 和 [`crates/http/src/consent.rs`](../../crates/http/src/consent.rs) 在成功及错误回跳中带 `iss` | 本版新增 SHOULD 已满足，而且实现强于最低要求 |
| Resource indicator / audience | `/authorize` 支持重复 `resource`，`/token` 收窄到单 audience；TS/Python verifier 要求单元素 `aud` 与本 RS resource ID 相等 | core resource binding 已具备 |
| DCR fallback | [`crates/http/src/register.rs`](../../crates/http/src/register.rs) 实现 RFC 7591 open/IAT 注册和 RFC 7592 生命周期；metadata 可发现 `/register` | 仍可服务 legacy/DCR-only client，但不再应作为首选方向 |

- `cargo test -p agent-auth-discovery`：55 passed；
- `npm test -- --run`（`sdk/ts`）：80 passed；
- `python3 -m pytest -q`（`sdk/python`）：80 passed。

### 9.2 缺口与优先级

| 优先级 | 缺口 | 当前证据与风险 | 推荐动作 |
| --- | --- | --- | --- |
| P1 | **AS 不支持 CIMD** | metadata 没有 `client_id_metadata_document_supported`；`/authorize` 只从 `ClientStore` 读取预注册/DCR client。随着 DCR 进入 Deprecated，新的零配置 client 会优先尝试 CIMD。CIMD 是 **SHOULD**，不是 core conformance blocker，但已是最重要的互操作方向。 | 新建独立 capability spec：URL-form `client_id` 检测、HTTPS/path 要求、document/client_id 精确匹配、redirect URI 校验、HTTP cache、SSRF/redirect/DNS rebinding 防护、tenant trust policy；实现后才宣告 metadata flag。 |
| P1 | **RS SDK 的 scope challenge 不完整** | TS [`sdk/ts/src/index.ts`](../../sdk/ts/src/index.ts) 和 Python [`sdk/python/agent_auth_rs/sdk.py`](../../sdk/python/agent_auth_rs/sdk.py) 的 401 challenge 不带 route scope；403 虽可带 `scope`，但不带 `resource_metadata`。这会削弱新版推荐的首次最小 scope 选择和 step-up 自动化。 | 让 401/403 challenge 都能从 route policy 得到当前 operation 的完整 scope 集，并在 403 保留 `resource_metadata`。 |
| P1 | **scope hierarchy 未建模** | 两个 RS SDK 都只做字符串集合包含；新版要求 RS 在判断 token 是否足够时 **MUST** 考虑 broader scope implied narrower scope。对存在层级的 RS，这不是单纯推荐项。 | 增加显式、默认无隐含关系的 hierarchy/resolver 配置；禁止根据冒号或字符串前缀猜层级。 |
| P1 | **path-based PRM 默认 URL 拼接错误** | TS 当前默认拼成 ``${resourceId}/.well-known/oauth-protected-resource``，Python 同形。若 resource 是 `https://host/mcp`，RFC 9728/MCP fallback 是 `https://host/.well-known/oauth-protected-resource/mcp`，其次才是 root。origin-only resource 暂不受影响，显式 `resourceMetadataUrl` 也可绕开。 | 用结构化 URL API 实现 path insertion；保留显式 URL 优先，并覆盖 root、单层/多层 path、query/fragment 拒绝测试。 |
| P2 | **DCR `application_type` 未建模** | `RegisterRequest` 没有该字段；serde 会忽略未知字段，因此现代 client 发送它通常不会被拒，但 Agent Auth 不持久化，也不执行 OIDC native/web redirect 约束。MCP 的直接 MUST 在 client 一侧，所以这不是 AS 硬性不合规。 | 接受并验证 `native\|web`，持久化到 client record，并把 loopback/custom-scheme/HTTPS redirect policy 与类型绑定。 |
| P2 | **EMA 尚未实现** | discovery 未宣告 `authorization_grant_profiles_supported`，`/token` 没有 ID-JAG grant。现有 OIDC federation 和 RFC 8693 token exchange 可复用部分校验设施，但不等价于 EMA。 | 作为独立 opt-in spec 设计：IdP trust anchor、ID-JAG profile、audience/resource/scope/subject 校验、account linking、重放防护、access-token audience 绑定和 metadata 宣告。 |
| 观察 | **Client Credentials 扩展仅部分重合** | 仓库已有 `client_credentials`，但当前路径面向已登记 workload identity（OIDC/SPIFFE/SigV4/mTLS），不是 Draft 扩展描述的普通 pre-registered `client_secret_basic` / `private_key_jwt` M2M 全面实现。 | 不要宣称支持该 Draft；待扩展稳定后再做 wire-level conformance 对照。 |

### 9.3 对现有路线图的具体调整

1. 保留 DCR 和现有凭据生命周期作为兼容 fallback，不删除 `/register`。
2. 把尚未完成的 `software_statement` 优先级降到 CIMD 之后。MCP
   已选择 CIMD 作为新实现方向，继续先扩展 DCR 会增加维护面，却不能提高现代 client
   的首选路径兼容性。
3. 在 conformance inventory 增补 scope challenge、scope hierarchy 和 path-based PRM 三项，
   因为它们属于现有 RS SDK 的直接职责。
4. EMA 另立 spec，不塞进现有 RFC 8693 token-exchange requirement；两者 trust
   model、grant profile 和 discovery signal 不同。
5. core `2026-07-28` transport 迁移应在实际 MCP client/server 项目逐仓审计。
   不能因为它们使用 Agent Auth，就推定已经支持新 wire revision。

## 10. 推荐迁移顺序

1. **先做 dual-era 隔离。** 用独立 modern/legacy wire codec 与 transport path
   服务两类 peer；不要在一个 schema 上“加几个可选字段”模拟兼容。
2. **再改 core lifecycle。** 每请求 metadata、`server/discover`、标准 HTTP
   headers、`resultType`、cache hints、subscriptions、MRTR、断线重发与幂等测试。
3. **随后加固 core Authorization。** 固定 canonical resource ID；PRM 与 challenge
   一致；验证 discovery metadata issuer 和 response `iss`；credential/token store
   以 issuer 分区；scope step-up 做 union 与 retry limit。
4. **客户端注册从 DCR 迁到 CIMD。** 保留 DCR 仅作兼容 fallback，并在 DCR 请求补
   `application_type`。AS 为 CIMD fetch 增加 SSRF、cache、redirect URI 和 trust
   policy 控制。
5. **最后按产品场景选择独立扩展。** 企业用户委托链采用 Stable EMA；纯
   machine-to-machine 场景若能接受 draft 风险，再采用 Client Credentials
   Draft。二者都不能替代 core 的 PRM、resource audience 和 RS token validation。
